# 일괄 실행 중단 점검과 복구

## 확인한 상태

- 기존 실행 3086과 3595는 `crashed`. 서버가 상세 오류를 남기지 않아 프로세스 종료 원인 자체는 확정할 수 없다.
- 3595는 마지막 이미지 교체 실행 3840에서 중단. 해당 하위 실행은 이미지 요청 노드에 도달하기 전에 종료되어 기존 본문을 다시 만들지 않고 이미지 단계부터 재개할 수 있었다.
- 점검 당시 70편 배치 중 18편 발행, 기존 글을 합쳐 공개 사이트 52편. 월 비용·예약금 합계 약 $5.45863.
- 이전 부모 흐름은 전체 테이블 106행(약 1,809,872자)을 5초마다 반복 조회했다. 대기가 65초 미만이어서 데이터베이스에 실행을 내려놓지 않았다. 부모 실행에는 단계별 저장도 설정돼 있지 않았다.

## 반영한 변경

- 전체 행 조회와 다음 작업 판정을 읽기 전용 보조 `Blog - 소소한 기준 [Util] - Choose Batch Action`(JVvzcFDPaGKW8uAr)로 분리. 부모에는 다음 작업 ID·revision·상태 등만 반환한다. 실제 재개 작업 출력은 232자였다.
- 부모의 대기는 70초로 변경하고 실행 진행 저장을 켰다. 보조 실행에는 120초 제한을 두고 성공한 전체 테이블 기록은 저장하지 않는다.
- 큰 원고·출처·발행 payload가 부모의 반복 이력에 계속 들어오지 않게 했다. 이는 관측된 과도한 데이터 전달과 저장되지 않는 대기 구조의 수정이며, 서버 로그 없는 메모리 부족을 확정 진단한 것은 아니다.
- 작성 프롬프트는 서로 다른 기능을 같은 도구라는 이유만으로 거절하지 않도록 수정. 최종 중복·근거·이미지 판정은 기존 독립 편집 검수에서 유지한다.
- HTTP 403 `Exhausted balance`는 `provider_blocked`로 분리한다. 요청 ID 없이 명확히 거절된 요청의 예약금만 해제한다. timeout 등 불확실한 요청은 예약금을 보존한다.
- `provider_blocked` 또는 `image_uncertain`가 있으면 새 유료 단계 전체를 중단한다. 이미 승인된 원고의 무료 발행 확인은 허용한다.

## 검증과 현재 외부 장애

- 수정 실행 4338에서 70초 데이터베이스 대기 후 자동 재개를 확인했다. 상태는 `crashed`가 아닌 `waiting`으로 저장됐고 waitTill 이후 다음 단계로 복귀했다.
- 재개된 이미지 요청 실행 4340의 실제 fal 응답: HTTP 403, `User is locked. Reason: Exhausted balance.`
- 따라서 현재는 블로그 월 $7 상한이 아니라 fal 계정의 선불 잔액 부족이 새 이미지 요청을 차단한다. 자동 충전하지 않는다. 잔액이 보충되기 전에는 새 원고 생성으로 비용을 더 쓰지 않는다.
- 이 상태는 70편 완료가 아니다. 원고와 승인 revision·이미지·비용 기록을 보존하며, fal 계정 장애가 해소된 뒤 같은 배치에서 이어간다. 월 한도 $7은 유지한다.

공식 동작 근거: https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait (65초 미만 대기는 실행 데이터를 데이터베이스로 내려놓지 않음).
